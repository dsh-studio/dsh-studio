# 搭子（Dazi）桌面工作台 — 设计文档

日期：2026-08-17 · 状态：已评审通过（用户拍板）
工作名：**搭子 / Dazi**（最终品牌名在 W1 核验 GitHub org / 域名可用性后定案；备选：工友、牛马）

## 1. 背景与定位

DeepSeek Harness（dsh，2026-08-13 发布，MIT）是开源、模型无关的 agent 运行时底盘，但其自带 Web UI 面向开发者。"dsh + 大众化壳"的生态位当前无人占据（OpenClaw 偏渠道个人助手，OpenCode 偏 CLI coding）。腾讯 WorkBuddy（桌面智能体工作台，月访问 2000 万+）验证了"坐在电脑里干活的 AI 同事"这一品类，但闭源、云端、进不了对隐私/内网敏感的场景。

**产品定位**：开源、中文优先的桌面 AI 工作台——下载即用，自然语言派活，AI 在本机沙箱里真的动手干（文件、文档、调研、数据），每一步可审批、可回放。runtime 是 dsh，但用户永远不需要知道这一点。

## 2. 目标用户与商业模型

- **首发人群**：中文 prosumer（会自己配 key 的独立开发者/运营/自媒体/量化爱好者）；产品设计为"不配 key 直接用"留路（见模型商店阶梯），逐步下探大众职场用户。
- **商业模型（token 分销阶梯）**：
  1. **阶段①（首发即有）**：BYOK 免费 + 内置"推荐供应商"一键接入，挂邀请返佣（硅基流动等聚合商的分销机制），零计费系统；
  2. **阶段②（有量后）**：与供应商谈折扣额度，壳内充值通道吃差价（需支付/计费，伴生决策，非现在）；
  3. **阶段③**：自营中转池（远期，可能永不做）。
- **设计硬约束**：模型接入体验（首启引导、模型商店、路由配置）必须由壳自己掌控，不交给 dsh 原生 UI。

## 3. 技术路线决策

选定 **方案 A + C 第一步**：Tauri 桌面 App 为主体（自研 UI，dsh 作内嵌 runtime 子进程），第 1 周先发中文技能包 + 预置 bundle 占位探水温。

- 排除 方案 B（fork dsh Web 前端）：深绑上游前端内部接口，是 v0.1 动荡期最脆的耦合点；分发够不着"下载即用"。
- 排除 纯 C（只做发行版）：对"小白友好"与 token 转化都做不深。

## 4. 架构

```
Tauri App（TS/React，自研 UI）
 ├─ 界面层：任务框 / 会话流 / 审批卡 / 会话历史 / 设置
 ├─ 商业层：模型商店（供应商目录+返佣链接+BYOK）/ 首启引导
 ├─ runtime-bridge（全项目唯一接触 dsh 的模块）
 │    启动·健康检查·重启 sidecar；JSON-RPC 会话协议；patch 文件生成
 └─ sidecar：捆绑 Node 24 + 锁定版本的 dsh + 预置 profile
      ├─ 预置 bundle：中文系统提示 + 工具面 + 审批策略
      ├─ 中文技能包（独立 repo，dsh skill 格式）
      └─ 中文办公连接器（MCP，后续逐个加）
```

### 组件职责

| 组件 | 职责 | 依赖 |
|---|---|---|
| 界面层 | 会话渲染、流式输出、工具调用中文化展示、审批交互 | 仅 bridge 的类型化接口 |
| 商业层 | 首启引导、供应商目录（含返佣链接）、BYOK 配置、生成 pi-ai providers patch + `.env` 写入 | 仅 bridge 的 patch 生成接口 |
| runtime-bridge | sidecar 生命周期（启动/健康检查/崩溃重启）；JSON-RPC 客户端；dsh profile/patch 文件读写 | dsh 的三个稳定面（见铁律） |
| sidecar | 打包的 Node 运行时 + 固定版本 dsh + 预置 profile | 无（自包含） |
| 中文技能包 | 独立 repo，skill 格式，发行版与 App 共用 | dsh skill 格式 |

### 三条铁律

1. **窄耦合面**：壳只依赖 dsh 的三个稳定面——SDK JSON-RPC 协议、profile/patch 组装、MCP/skill 格式。绝不 import 其内部包；bridge 是唯一接触点。
2. **锁版本发布**：dsh 版本随壳锁定，升级 dsh 是壳的一次显式 release（含回归测试），不追 latest。v0.1 破坏性变更被隔离在 bridge 一层。
3. **干净房间**：个人项目，不引入任何雇主仓库的代码、key、基础设施引用；经验与模式可复用，实现必须重写。

## 5. MVP 范围（alpha，4-6 周）

**做**：

- 首启引导：推荐供应商一键接入（挂返佣）/ BYOK，两条路同级呈现；
- 任务对话流：流式输出 + 工具调用的中文化渲染；
- 审批卡：改文件/跑命令须确认，带 diff 预览；
- 会话历史与恢复（基于 dsh 会话日志）；
- 预置中文技能 ×3：**批量文件整理、长文调研报告、数据表处理**（均为 dsh 执行世界强项）；
- macOS + Windows 打包 + 自动更新。

**明确不做（alpha）**：技能市场 UI（技能先内置）、自建计费（阶段①只做返佣）、Linux、多 agent 并行的精细 UI、插件开发者工具。

## 6. 数据流与错误处理

- **任务流**：用户输入 → bridge 经 JSON-RPC 提交 → dsh 流式事件 → 界面层渲染（文本/工具调用/审批请求分类型渲染）；审批请求阻塞该工具调用直至用户裁决。
- **sidecar 崩溃**：bridge 健康检查发现即自动重启，会话从 dsh 会话日志恢复；连续 3 次重启失败转为用户可见错误态（不静默循环）。
- **模型请求失败**：dsh 侧 llm-retry 负责重试；最终失败以中文人话呈现（区分：key 无效 / 余额不足 / 网络 / 模型不可用），并给出对应动作入口（去模型商店改配置）。
- **配置写入**：patch/`.env` 写入前校验 YAML/格式合法；写坏配置导致 sidecar 起不来时，bridge 回滚到上一份可用配置（保留最近 N 份快照）。
- **升级**：App 自动更新只更新壳；dsh 升级捆绑在壳的 release 里，升级前迁移检查（dsh v0.1 明确会破坏磁盘格式——若会话格式不兼容，明示用户"旧会话将归档不可续"而非静默丢失）。

## 7. 测试策略

- **bridge 协议层**：单测 + mock runtime（协议样本回放），覆盖启动/崩溃重启/流式分片/审批往返；
- **端到端 smoke**：真 dsh sidecar 跑最小任务（无 key 时用 dsh 的 keyless 回放思路或跳过标记）；
- **打包冒烟**：双平台 CI 构建产物启动即测（sidecar 能起、健康检查通过）；
- **技能包**：每个 skill 附带一个可复现的验收任务脚本。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| dsh 破坏性变更 | 锁版本 + 窄协议面；每次升级走显式 release 流程 |
| 上游或他人先做出同类壳 | 速度；中文本地化 + 技能包 + 返佣供应商目录是慢功夫护城河 |
| Tauri sidecar 打包坑（Node 捆绑、双平台签名） | W1 spike 先证伪，再铺 UI |
| 返佣供应商政策变动 | 供应商目录做成数据配置（远程可更新），不硬编码单一家 |
